# GNSS 失锁与恢复更新 MVP

## 1. 这个模块回答什么问题

GNSS/IMU 松组合不能假设 GNSS 始终可用。车辆进入隧道、楼群或树荫后，GNSS PVT
可能直接中断；重新输出位置时，也可能带着尚未稳定的多路径误差或过于乐观的协方差。
本模块回答两个问题：系统怎样知道自己已经失去 GNSS，以及第一帧恢复观测应不应该像
正常观测一样强力修正 INS。

当前实现是故障注入与策略验证 MVP，不是接收机完好性认证，也不是实车部署结论。

## 2. 先建立物理直觉

把 INS 想成只靠速度和方向在纸上推算位置。GNSS 消失后，笔仍连续移动，但零偏使路线
逐渐弯曲。GNSS 恢复时，一次把笔尖拉回新坐标可能产生突跳；分几次确认再拉回会平滑
一些，却会更慢消除真实误差。这个类比没有表达状态相关性、三维姿态和随机协方差，
这些仍由 ESKF 处理。

## 3. 一维最小例子

设预测位置为 `10 m`，方差 `P = 4 m^2`；恢复的 GNSS 给出 `0 m`，标称方差
`R = 1 m^2`。直接更新的增益为：

```text
K = P / (P + R) = 4 / 5 = 0.8
x+ = x- + K(z - x-) = 10 + 0.8(0 - 10) = 2 m
```

状态一步跳了 `8 m`。若恢复期把 GNSS 标准差放大 `s = 10`，注意方差要放大
`s^2`：

```text
R_recovery = s^2 R = 100 m^2
K_recovery = 4 / (4 + 100) = 0.0385
x+ = 10 + 0.0385(0 - 10) = 9.615 m
```

第一帧只做小修正。代价同样清楚：如果 GNSS 是正确的，误差收敛会更慢。因此降权是
完整性和连续性策略，不是无条件提高精度的技巧。

## 4. 定义、单位与约定

- GNSS 时间戳 `time_s`：接收机报告的观测时刻，单位 `s`。
- 断联超时 `outage_timeout_s`：距最后一帧 GNSS 的时间，单位 `s`。
- GNSS 位置标准差 `std_ned_m`：NED 三轴一倍标准差，单位 `m`。
- 标准差倍率 `s`：无量纲；观测协方差实际变成 `s^2 R`。
- NIS：`r^T S^-1 r`，无量纲；本项目位置观测维数为 3。
- 断联注入区间采用相对真值起点的半开区间 `[start_s, end_s)`。
- 姿态、坐标系、时间偏差和杆臂约定不在本策略层改变。

状态机包含：

```text
TRACKING --超时--> OUTAGE --收到观测--> RECOVERY
RECOVERY --连续通过门限--> TRACKING
TRACKING/RECOVERY --连续拒绝--> DEGRADED
DEGRADED --再次收到观测--> RECOVERY
```

## 5. 为什么这样更新

正常位置更新的创新和创新协方差为：

```text
r = z_gnss - h(x-)
S = H P- H^T + R
NIS = r^T S^-1 r
```

恢复期不修改 `z_gnss`，只令 `std' = s * std`，因此：

```text
R' = diag((s * std_n)^2, (s * std_e)^2, (s * std_d)^2) = s^2 R
K' = P- H^T (H P- H^T + R')^-1
```

`R'` 增大使 Kalman 增益减小。当前倍率按已连续接受次数 `k` 衰减：

```text
s_k = max(1, s_0 * decay^k)
```

默认 `s_0 = 10`、`decay = 0.5`，前三帧使用 `10、5、2.5`。连续三帧通过 NIS
门限后回到 `TRACKING`。门限判定仍属于 ESKF，状态机只读取接受结果，避免复制数学核心。

## 6. 时间与误差的尺度

若水平加速度零偏近似常量 `b_a`，忽略姿态耦合时：

```text
delta_v(t) = b_a * t
delta_p(t) = 0.5 * b_a * t^2
```

单位检查为 `(m/s^2)*s = m/s` 和 `(m/s^2)*s^2 = m`。所以断联时间翻倍时，
该简化项的位置误差增至四倍。陀螺零偏还会把重力投影到水平面，使误差增长更快，
实际三维结果必须由机械编排和协方差传播评估。

## 7. 代码对应关系

- `python/gnss_imu/gnss_integrity.py`：状态、配置、转移和恢复倍率。
- `python/examples/run_dataset1_eskf.py`：丢帧注入、调用 ESKF、写事件审计文件。
- `python/gnss_imu/loosely_coupled_eskf.py`：NIS、Kalman 更新和协方差数学核心。
- `python/gnss_imu/delayed_eskf.py`：在有效观测时刻更新并重放 IMU。
- `python/examples/run_dataset1_gnss_outage.py`：三场景对比实验。

处理顺序必须是：按报告时刻判断是否丢帧，恢复策略调整该帧协方差，再由固定延迟层把
它更新到有效观测时刻。若先在当前时刻更新再处理延迟，恢复策略正确也无法补救时间错误。

## 8. 可失败的验证

单元测试检查以下错误：超时前误报断联、恢复倍率少乘或多乘一次、未满连续接受数就退出
恢复、连续拒绝后没有降级、时间倒退未报错。Dataset1 集成测试注入 `[1, 3) s`
断联，要求恰好丢弃两帧，并出现 `outage-detected`、`measurement-reacquired` 和
`recovery-complete` 事件。

短时烟雾实验使用 `[4, 8) s` 断联。干净 RTK 下直接恢复的恢复后 5 秒位置 RMS
约为 `0.0255 m`，谨慎恢复约为 `0.0276 m`；但重捕获窗口最大误差步长从
`0.0423 m` 降至 `0.0296 m`。这说明降权没有凭空提高精度，而是在收敛速度与连续性
之间取舍；后续还必须在跳点、NLOS 和协方差失真场景下验证。

运行：

```powershell
.\.venv\Scripts\python.exe python\examples\run_dataset1_gnss_outage.py `
  --duration-s 30 --outage-start-s 10 --outage-end-s 20
```

输出包括 `comparison.json`、三组 `summary.json`、完整性事件 CSV 和误差对比图。

## 9. 工程边界与后续工作

当前失锁判定只使用 PVT 到达间隔，没有使用卫星数、解状态、DOP、差分龄期、载噪比或
接收机告警。恢复策略只有协方差膨胀和连续 NIS 判断，尚未加入滞回、多窗口创新统计、
缓慢 NLOS 偏移检测及位置跳点故障注入。真实系统还必须明确乱序包、重复包、时钟跳变、
GNSS 协方差可信度和安全需求。MEMS 与高精 IMU 应分别使用标定噪声，并比较不同断联时长。

## 10. 面试与自检问题

1. 为什么标准差放大 10 倍会使协方差放大 100 倍？
2. 为什么只做单帧 NIS 门限不能代表完整的 GNSS 完好性管理？
3. 恢复降权为何可能让位置 RMS 变差，却仍有工程价值？
4. 若 GNSS 以 1 Hz 输出，断联超时应如何避免正常抖动造成误报？
5. 固定延迟更新与恢复状态机的职责为什么应当分开？
6. 如何构造一个缓慢漂移但单帧 NIS 始终不过大的 NLOS 反例？
